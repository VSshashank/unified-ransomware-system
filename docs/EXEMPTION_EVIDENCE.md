# Evidence Record: Unvalidated Container Exemption in URDS

## Evidence status

This document records a reproducible Monitor-level finding in the URDS branch `feat/detection-hardening` and its derived working branch `claude/novelty-claim-existing-projects-kau2ng`.

The finding is not a claim that all ransomware detectors share this behavior. It is a claim about the current URDS Monitor implementation and its recognized-format registry.

## Finding

The current detector recognizes **16 unique container/media formats through 20 signature entries**. Structural validation is implemented for five of those unique signature formats—`zip`, `gzip`, `png`, `jpeg`, and `pdf`—and for the separate ISO-BMFF path. The other **11 of the 16 signature-recognized formats are unvalidated** in the current registry:

| Format | Recognized signature entries | Structural validator in registry | Result for fresh high-entropy payload |
|---|---:|---:|---|
| zip | 3 | Yes | Forged random payload is suspicious; genuine valid ZIP can be benign. |
| gzip | 1 | Yes | Evaluated by validator. |
| png | 1 | Yes | Evaluated by validator. |
| jpeg | 1 | Yes | Evaluated by validator. |
| pdf | 1 | Yes | Evaluated by validator. |
| 7z | 1 | **No** | `container_valid=None`; exemption accepts high entropy as `benign_compressed`. |
| rar | 1 | **No** | `container_valid=None`; exemption accepts high entropy as `benign_compressed`. |
| xz | 1 | **No** | `container_valid=None`; exemption accepts high entropy as `benign_compressed`. |
| bzip2 | 1 | **No** | `container_valid=None`; exemption accepts high entropy as `benign_compressed`. |
| lz4 | 1 | **No** | `container_valid=None`; exemption accepts high entropy as `benign_compressed`. |
| zstd | 1 | **No** | `container_valid=None`; exemption accepts high entropy as `benign_compressed`. |
| gif | 2 | **No** | `container_valid=None`; exemption accepts high entropy as `benign_compressed`. |
| mp3 | 2 | **No** | `container_valid=None`; exemption accepts high entropy as `benign_compressed`. |
| ogg | 1 | **No** | `container_valid=None`; exemption accepts high entropy as `benign_compressed`. |
| flac | 1 | **No** | `container_valid=None`; exemption accepts high entropy as `benign_compressed`. |
| riff | 1 | **No** | `container_valid=None`; exemption accepts high entropy as `benign_compressed`. |

The key defect is the tri-state interpretation in `services/monitor/detection.py`:

```python
if high_entropy and container and container_valid is not False and not ransom_ext:
    return verdict_of(False, "benign_compressed", ...)
```

`container_valid is not False` treats both `True` and `None` as sufficient evidence for the exemption. `None` means that no validator exists or that validation did not produce a definitive result. It does not mean that the container is valid.

## Reproduction method

The evidence is generated by:

```bash
cd /home/ubuntu/unified-ransomware-system
URDS_WRITE_REPORTS=1 \
  python3 scripts/recf_exemption_evidence.py --write-report
```

The script is intentionally Monitor-only. It creates a 64 KiB deterministic high-entropy payload for each recognized signature in a temporary directory, keeps the path fresh, evaluates the repository’s own `identify_container`, `container_status`, `validate_container`, and `classify` functions, and removes the temporary directory automatically. It does not start a watcher, invoke the full response pipeline, mutate production service code, or write a report unless `URDS_WRITE_REPORTS=1` is explicitly set.

The raw machine-readable output is stored in [`reports/recf_exemption_evidence.json`](../reports/recf_exemption_evidence.json).

## Observed result

The reproduced run recorded:

| Measure | Result |
|---|---:|
| Recognized signature entries | 20 |
| Unique recognized formats | 16 |
| Validated unique formats in signature table | 5 |
| Unvalidated unique formats | **11** |
| Validated entries returning `benign_compressed` | 1 |
| Validated entries returning suspicious | 6 |
| Unvalidated entries returning `benign_compressed` | **13** |
| Unvalidated entries returning suspicious | 0 |
| Payload entropy | Approximately 8.0 bits/byte |
| Path history | Fresh |

The different entry and unique-format counts arise because ZIP, GIF, and MP3 each have duplicate signatures. The claim is therefore **11/16 unique recognized formats**, not “11 files.”

The result is architectural rather than statistical. The unvalidated formats all follow the same code path: a recognized header produces a non-null container name, the absent validator produces `container_valid=None`, and the high-entropy exemption accepts `None` as though it were `True`.

## Why this is a meaningful governance finding

Whitelist and training-mode suppressions are routed through `admissibility.adjudicate()`, where a suppression forgery cost is compared with a detection-signal avoidance cost. The container exemption is a different false-positive mitigation: it cancels high-entropy evidence directly inside `classify()` and never reaches the common policy decision point.

The result is that the current system has a common admissibility principle but incomplete coverage of the mechanisms that can cancel evidence. The unvalidated-format cases demonstrate that the missing coverage has practical consequences: an attacker needs only a recognized magic prefix and high-entropy bytes, while the system records no structural proof and performs no cost adjudication.

## Surgical first repair

The first repair should be deliberately narrow:

```diff
- if high_entropy and container and container_valid is not False and not ransom_ext:
+ if high_entropy and container and container_valid is True and not ransom_ext:
```

With this change, `container_valid=None` no longer authorizes `benign_compressed`. The existing high-entropy branch then remains available to classify the file as suspicious. This is preferable to a blanket fresh-path rule because it does not penalize all fresh valid containers; it specifically refuses to treat **unvalidated** claims as validated.

The repair must be evaluated against both sides of the trade-off:

- genuine valid ZIP, GZIP, PNG, JPEG, and PDF files should retain their validated benign behavior where the validator succeeds;
- high-entropy payloads prefixed with 7z, RAR, XZ, BZip2, LZ4, Zstandard, GIF, MP3, OGG, FLAC, and RIFF signatures should no longer receive a free exemption;
- benign files in the 11 currently unvalidated formats may become false positives and that cost must be measured and disclosed; and
- the repair must not alter path whitelist, hash whitelist, training-mode, recovery, or ledger behavior.

The correct long-term option for a format that matters operationally is to add and test a real validator. Until then, the system must fail closed on an unvalidated claim rather than silently treating it as a validated explanation.

## Scope and limitations

This evidence establishes a **Monitor-level** architectural finding. It does not by itself establish that the ML layer, response layer, recovery ledger, or every external ransomware detector has the same defect. The novelty claim should therefore be scoped to the URDS Monitor admissibility architecture unless the later pipeline audit produces independent evidence.

The payload is a controlled high-entropy witness, not a live ransomware sample. The evidence demonstrates that the exemption can be reached without structural validation; it does not measure real-world prevalence of any format or prove that every attacker would choose the same prefix.
