# Reproducibility appendix

**Item P8.4 (NI). Phase 8, Week 32.**

> **Exit gate — Week 32, FINAL.** An independent reader can reproduce every
> headline figure from the repository and the appendix alone. Verify this by
> actually re-running the appendix commands from a clean checkout, not by
> inspection.

This appendix is the "and the appendix alone" half. The verification half is a
script, not a paragraph:

```bash
URDS_WRITE_REPORTS=1 python scripts/verify_reproduction.py
```

It clones the repository at `HEAD`, builds a fresh virtual environment, installs
each service's declared requirements, rebuilds the corpus from its seed, re-runs
every deterministic generator, compares each result against the committed
artefact manifest, re-checks all fourteen claims, and runs the five service
suites. The result lands in `reports/reproduction_check.json`. **§7 records what
that run actually produced, including what it broke on.**

|---|---|

**One Windows caveat, found by running this.** Keep the clone path short.
Installing scikit-learn into a virtual environment underneath a deep path fails
with `OSError: [Errno 2] No such file or directory` on a `.lib` inside
`sklearn/metrics/_pairwise_distances_reduction/` — a `MAX_PATH` overflow wearing
a misleading error message. A clone at `C:\Temp\u\clone` works; one nine
directories deep does not. `scripts/verify_reproduction.py` takes its scratch
root from `URDS_SCRATCH` so you can control this.

## 2. Setup, exactly

```bash
git clone <repository> urds && cd urds
python -m venv .venv
```

Windows: `.venv\Scripts\python.exe`. POSIX: `.venv/bin/python`. Everything below
writes `python` and means that interpreter.

```bash
python -m pip install -r services/gateway/requirements.txt
python -m pip install -r services/ledger/requirements.txt
python -m pip install -r services/monitor/requirements.txt
python -m pip install -r services/ml-engine/requirements.txt
python -m pip install -r services/response/requirements.txt
python -m pip install -r scripts/requirements.txt
python -m pip install pytest pytest-asyncio httpx psutil
```

`scripts/requirements.txt` is the measurement tooling: Pillow and fpdf2 build the
corpus, scipy computes the Clopper-Pearson limits, psutil samples the load test.
**No service declares these and none imports them**, which is exactly how they
came to be missing — they were installed on the author's machine and written down
nowhere, so the first clean-checkout run failed at the corpus rebuild and every
benign figure downstream of it was unreproducible. Versions are pinned because
the corpus manifest's per-file hashes are hashes of those encoders' output.

The last line installs four test-only dependencies. The CI matrix installs the
same four.

`services/dashboard/requirements.txt` is **not** installed. It pulls streamlit
and pandas, no command in this appendix touches it, and it is not in the CI
matrix.

## 3. Seeds

There are two sources of pseudo-randomness in this repository and both are
seeded. Nothing calls `os.urandom` in a path that produces a recorded figure.

| Seed | Value | Where | What it determines |
|---|---|---|---|
| Corpus seed | `20260902` | `scripts/build_benign_corpus.py` `DEFAULT_SEED` | Every generated byte of the 275-file benign corpus. Each file draws from `random.Random(f"{seed}:{stem}:{index}")`, so a file's content depends on its own name and position and not on how many files came before it |
| Simulator keystreams | fixed per family | `scripts/ransomware_simulator.py` | The 13 simulator families' encryption. Keystream is `sha256(seed ‖ counter)`, so a family's ciphertext is fixed |

Everything else that looks random is not: attack witnesses in the calibration and
the experiment are built from fixed byte patterns, and the tamper sweep's chains
are 40 blocks over fixed payloads.

**The corpus is not committed.** `corpus/` is untracked and rebuilt from the
seed, which is why the manifest carries a per-file hash — the rebuild is checked
rather than trusted:

```bash
URDS_WRITE_REPORTS=1 python scripts/build_benign_corpus.py
python scripts/build_benign_corpus.py --verify
```

The second command rebuilds every file in memory and compares its SHA-256
against `reports/benign_corpus_manifest.json`. **If this does not pass, stop** —
every benign figure downstream is a figure about a different corpus.

## 4. The commands, in order

Order matters twice: `benign_tradeoff.py` reads the experiment's report, and
`admission_recompute.py` reads the calibration's.

```bash
export URDS_WRITE_REPORTS=1

python scripts/build_benign_corpus.py          # 1. corpus, from the seed
python scripts/build_benign_corpus.py --verify #    check every file hash
python scripts/capability_calibration.py       # 2. ten capability levels
python scripts/admission_recompute.py          # 3. reads (2)
python scripts/three_arm_experiment.py         # 4. reads the corpus from (1)
python scripts/benign_tradeoff.py              # 5. reads (4)
python scripts/ledger_coverage.py              # 6.
python scripts/pipeline_governance.py          # 7.
python scripts/tamper_sweep.py                 # 8.
python scripts/failure_injection.py            # 9.
python scripts/simulator_sweep.py              # 10.
python scripts/load_test.py                    # 11. timing-dependent
python scripts/verify_vss.py --status-only     # 12. Windows only

python scripts/artefact_manifest.py --verify   # compare every result
```

The last two are the point. `artefact_manifest.py --verify` recomputes each
artefact's stable digest and compares it against the committed manifest;
`claim_matrix.py` re-reads every claim's cited figure out of the report and
fails if the report no longer says it.

### The suite

Five separate runs, one per service. **A single pytest process over `services/`
does not work** and this is not a matter of taste: the five services use flat
module names matching their container layout — each has its own `app.py`,
`gateway` and `response` both have a `main.py` — so one process imports whichever
`app` reached `sys.path` first and every later service silently tests the wrong
module. Running it that way produces 19 failures and 113 collection errors.

```bash
cd services/gateway   && python -m pytest -q && cd ../..
cd services/ledger    && python -m pytest -q && cd ../..
cd services/monitor   && python -m pytest -q && cd ../..
cd services/ml-engine && python -m pytest -q && cd ../..
cd services/response  && python -m pytest -q && cd ../..
```

Expected from a clean checkout: **659 passed, 20 skipped, 0 failed**
— gateway 86, ledger 67, monitor 381, ml-engine 30 + 18 skipped, response 95 + 2
skipped. In a working tree that also has `models/`, 677 passed and 2 skipped. The
18-test difference is `services/ml-engine`, whose tests are `skipif`-gated on a
trained model file; `models/` is gitignored, so a clean checkout skips them. That
is a real gap and it is reported as one rather than hidden by committing a large
pickle whose provenance is EMBER.

### Artefact hashes

Two digests per artefact, both in `reports/artefact_manifest.json`:

- **`sha256`** over the committed bytes. Detects an edited report. Quote this
  when citing a specific file.
- **`stable_sha256`** over the JSON with each artefact's declared volatile
  fields removed, wall-clock durations dropped at any depth, and `mkdtemp`
  working directories normalised. **This is the digest to compare.**

  Volatile fields are declared per artefact in `scripts/artefact_manifest.py`. A
  plain name is removed at the top level; a name written `**/name` is removed at
  any depth. The distinction is not decoration. Run provenance —
  `generated_at`, `commit`, `branch` — uses the depth form, because
  `benign_tradeoff.json` carries `source_experiment.commit`, which differs for
  any reader reproducing at a different commit and is not a finding. A measured
  field like `latency_ms` uses the plain form, because the same name appearing
  somewhere else in a report would want deciding on its own merits rather than
  being erased silently. **Removal was top-level-only until the fourth gate run
  found two fields that were declared volatile and never actually excluded** —
  see §7.3.

`reports/artefact_manifest.json` rather than transcribed:

**Why no artefact is byte-identical.** Every report carries `generated_at`, most
carry `commit` and `branch`, several carry timings, and three embed a `mkdtemp`
path. A manifest of raw file hashes would fail on its first line for reasons that
have nothing to do with any result, which is why there are two digests and not
one.

**And one artefact genuinely was not reproducible until Phase 8 fixed it.**
`gzip.compress` writes the current time into the gzip header, so the
standard-library container witness — the attack that prices `structural_mismatch`
at negligible — produced a different `artefact_sha256` on every run, and nobody
could check the recorded one. It is pinned with `mtime=0`. The pin moved no
result: `summary` is identical, no capability level changed on either ladder, and
the attack still succeeds with `container_status: valid`.

## 6. What this appendix cannot reproduce

Six figures. Each is named, with the reason and what it would take.

1. **`reports/load_test.json` — every number in it.** Wall-clock measurements on
   one host, recorded in the report's `host` block. A reader reproduces the
   *shape* — p99 above the 100 ms budget, produce-to-drain far above 1:1, a
   `_SEEN_FILES` set that never shrinks — not the digits. It is classed
   `timing-dependent` and `--verify` will not flag it as drift.
2. **`reports/vss_status.json` — the VSS status.** It depends on the host and on
   whether the shell is elevated. On an elevated Windows shell this report
   *should* differ, and that difference is the reason to run it. **VSS-backed
   restore itself is not measured anywhere in this repository** — acceptance row
   12, still partial. Reproducing it needs an Administrator shell, which no
   recorded run had.
3. **The 18 skipped ml-engine tests.** They are `skipif`-gated on a trained model
   under `models/`, which is gitignored. A clean checkout skips them; retraining
   needs EMBER, which is not redistributable through this repository.
4. **"10 of 10 capability levels carry an empirical source trail" is 9 of 10 on a
   clean checkout.** The tenth strategy, `C_forge(ml_confidence_gate)`, scores a
   feature vector against that same gitignored model. Without it the level is
   recorded **unresolved under D2** rather than assumed — which is D2 working as
   designed, not a failure, but a reader cannot reproduce the ten.
   `reports/capability_calibration.json` is classed `environment-dependent` for
   this reason and its `tolerance` names the four summary counters that move.
   Claim C-15 in the matrix accepts either value and fails on any third.
5. **Two per-family fields in `reports/simulator_families.json`.**
   `detection_seconds` is wall-clock, and `collateral_events_flagged` counts
   watcher events that arrived while a *different* family was running, so it
   depends on how the filesystem event queue interleaves. Three consecutive runs
   on 5 September 2026 gave `{poisoner: 5, renamer: 2}`, `{poisoner: 5,
   renamer: 1}` and `{poisoner: 5, locker: 1}`. **What did not move across those
   three runs is what the thesis quotes** — 13 of 13 families detected, every one
   within 2 s, and every restore round-trip true. The report is classed
   `environment-dependent`, those fields are excluded from the stable digest at
   any depth, and the artefact's `tolerance` names them.
6. **A green CI run.** `.github/workflows/tests.yml` exists and **no CI run has
   been observed.** The matrix has never executed on a runner, so no badge is
   claimed and the Week 28 gate's CI half stays open. Opening a pull request
   against this branch is what would close it.

Two more limits that are not about commands:

- **The corpus is synthetic.** 275 procedurally generated files, byte-identically
  reproducible from a recorded seed, stratified by validator coverage and
  compressibility. It is not a sample of anyone's real filesystem. Every
  false-positive figure is a figure about this corpus.
- **No independent human reproduced anything.** §9.15's AS↔NI and SI↔SH ring was
  not achieved. Every capability level was derived twice, in opposite decision
  orders, over the same recorded facts and without reference to the first
  conclusion — which is the protocol — but by one author in one session. Every
  record carries `reproduction.independent_human_reviewer: false`.

### 7.2 Wall time is not a property of this repository

The same 27 stages took **893 s** on the fifth run and **7 496 s** on the sixth,
and the stage that dominated was different each time — the monitor suite took
488 s on the fifth run and 64 s on the sixth, while `simulator_sweep.py` took
seconds on the fifth and 7 277 s on the sixth.

**Both runs shared the host with other work.** That is the honest explanation and
it is the useful one: a stage that writes files and waits for a filesystem
watcher to notice them is measuring the host's scheduling, not the repository's
behaviour, and the two runs disagree by a factor of eight on which stage that
was. Budget an hour and do not read a slow stage as a fault.

What did *not* vary is every number the thesis quotes. The digest comparison and
the claim re-check passed on both runs.

## 8. Reading a failure

| What `--verify` says | What it means | What to do |
|---|---|---|
| `match` | The stable digest is exactly the recorded one | Nothing. The result reproduced |
| `expected-drift (timing)` | A timing- or host-dependent artefact moved | Expected. Compare the shape, per §6 |
| `DRIFT <old> -> <new>` | A **deterministic** artefact changed | A result moved. Diff the report against the committed one; something in the code or the corpus is different |
| `MISSING` | The artefact is not there | Run its generator, in the §4 order |

If `claim_matrix.py` fails while `artefact_manifest.py --verify` passes, the
reports are intact and a *claim* is stale — the document is wrong and the report
is right. That is the direction the check is built to enforce.
